# Migration Plan: Lovable Cloud → Standalone Supabase

_Last updated: 2026-06-10. Status: **Documented, not yet executed.**_

This is the pre-flighted runbook for moving YubiLearn off Lovable Cloud onto a directly-owned Supabase project (typical motivation: enterprise contracts requiring direct vendor relationship, BAA, or specific region/residency).

## 0. Decide if we actually need to migrate

Lovable Cloud already runs on Supabase. We get:
- SOC 2 Type 2 inheritance from Supabase.
- All RLS, storage, edge function, and vault features.
- The Supabase project is real and addressable; only ownership/billing differs.

**Only migrate if a contract explicitly requires direct vendor relationship.** Otherwise this is wasted risk.

## 1. Pre-flight inventory

Run before any cutover. Capture each artifact into `/migration-snapshot/<date>/`.

- [ ] Schema dump: `supabase/migrations/` (already in git).
- [ ] Storage bucket list + policies: `supabase storage list` per bucket.
- [ ] Secrets: `fetch_secrets` → redacted manifest (names only).
- [ ] Edge function list: `ls supabase/functions/`.
- [ ] Auth provider config: Google / Apple / Clever OAuth client IDs, redirect URIs, JWT secrets.
- [ ] Custom domain: `yubilearn.com` → DNS records.
- [ ] Cron jobs: pg_cron entries (run `select * from cron.job`).
- [ ] Realtime channel config (Lovable Cloud project settings).
- [ ] Vault entries (names only).

## 2. Stand up the new project

1. Create the new Supabase project in the target org / region (us-east-1 default).
2. Enable extensions used: `pgcrypto`, `pgjwt`, `pg_cron`, `pgmq`, `vector` if present.
3. Note the new `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.

## 3. Schema + data

1. Apply every migration in `supabase/migrations/` in order to the new project.
2. Verify with `supabase--linter`: target 0 errors, ≤ 98 documented warns (matches `SECURITY_POSTURE.md`).
3. Restore data via PITR snapshot from the source Supabase project (Supabase support can assist with cross-project restore) **or** logical dump if cross-project restore is not available.
4. Re-issue any sequences (`select setval...`) to current max+1.

## 4. Storage

1. Recreate buckets with identical names, visibility, and size limits.
2. Apply storage policies (they live in the migrations).
3. Copy objects: `supabase storage cp` recursively or use signed-URL transfer.
4. Spot-check `aura-audio/<uid>/...` paths after copy.

## 5. Edge functions

1. `supabase functions deploy` for each function.
2. Re-add every secret via `supabase secrets set` from the redacted manifest (Step 1) — values come from password manager / Vault, not git.
3. Re-create cron triggers in the new project.

## 6. Auth

1. Recreate Google / Apple / Clever provider configs with the new project's callback URL.
2. Update OAuth client redirect URIs at each provider.
3. Test sign-in for: email/password, Google, Clever, student-ID dual login.

## 7. Frontend cutover

1. Update `.env`:
   - `VITE_SUPABASE_URL` → new
   - `VITE_SUPABASE_PUBLISHABLE_KEY` → new anon key
   - `VITE_SUPABASE_PROJECT_ID` → new ref
2. `src/integrations/supabase/types.ts` regenerated by `supabase gen types` against the new project.
3. Smoke-test the preview build.

## 8. DNS

1. Lower TTL on `yubilearn.com` to 60s, **24 hours before cutover**.
2. At cutover: point CNAME / A records to new project's host.
3. Update custom-domain config in Supabase to claim the hostname (DV cert auto-issues).

## 9. Verification (must all pass before announcing cutover complete)

- [ ] Student sign-in flow (email + student-ID).
- [ ] Parent consent email arrives + token validates.
- [ ] Teacher dashboard loads classroom data.
- [ ] AURA audio upload writes to correct path-scoped bucket.
- [ ] `generate-teacher-summary` edge function returns a pseudonymized + decoded summary.
- [ ] Safety alert end-to-end (test classroom) — escalates per SLA.
- [ ] `security_audit_log` hash chain unbroken.
- [ ] `security--run_security_scan` clean.

## 10. Rollback

If any Step-9 check fails:

1. Re-point DNS back to the Lovable Cloud host (TTL is already 60s).
2. Re-enable writes on the source project (we kept it read-only during cutover).
3. Diff `security_audit_log` and `aura_records` rowcounts between source and target to identify drift.
4. Post-mortem within 24 hours.

## 11. Decommission

After 14 days clean on the new project:

1. Final snapshot of the Lovable Cloud project to cold storage.
2. Coordinate with Lovable support to retire the old project.
3. Update `/game/legal/subprocessors` if the chain changed.
